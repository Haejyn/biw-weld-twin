## 이번 실행: search 도구 추가

에이전트에 `search(design, k)` 도구를 더한 뒤 같은 시작 설계 12개 × 조건 2 를 다시 돌렸다. 시작 설계, 요청 문장, 조건 2 에서 고정한 변수는 아래 "이전" 실행과 같다. `search` 는 제약을 만족하는 후보를 시작 설계 주변에서 반경을 넓혀 가며(범위 폭의 3 % 에서 40 %, 반경마다 300개) 대리 모델로 훑고, 예측 0개인 후보가 k개 모이면 멈춘다. 모자라면 `explore.py` 와 같은 전역 후보 1,500개를 더한다. 예측 0개인 상위 후보는 필요 없는 변경을 하나씩 시작값으로 되돌려 본다. 결과는 시작 설계에 가까운 순서이고 대리 모델 예측이 캐시된다.

기준선도 보강했다. 이전 기준선(전역 후보 10,000개)이 못 찾는 경우가 많아서, 같은 국소 탐색(`search_candidates`, k=20)에서 나온 후보를 합쳤다. 시뮬레이터 확인 수는 이전 확인 수 + 국소 후보 확인 수이며, 실제 합집합 순서로 돌렸을 때보다 같거나 많다. 걸린 시간은 이전 기준선 시간 + 국소 탐색 시간이다.

## 방법

- 시작 설계: `data/gen/designs_1.json`(학습에 쓰지 않은 시험 설계 200개) 중 시뮬레이터 판정에서 못 쏘는 타점이 1개 이상인 설계 155개에서 20개를 시드 0 로 뽑고 시간 때문에 앞의 10개만 썼다. 여기에 README 의 A, B.
- 조건 1: 제약 없음. 조건 2: 같은 시작 설계에서 기준선(조건 1)이 가장 많이 바꾼 변수(변수 범위 폭 대비)를 그대로 두라는 한국어 요청 한 문장. 요청 문장은 템플릿 3개를 번갈아 쓴다.
- 기준선: 시작 설계 주변(변수별 정규분포, 범위 폭의 0.25배)에서 후보를 뽑아 제약 안으로 자르고, 대리 모델 예측이 0개인 것을 시작 설계와의 거리(`norm_dist`) 순으로 시뮬레이터에 확인해 처음으로 0개인 설계를 고른다. 최대 20개까지 확인한다.
- 성공: 시뮬레이터가 0개로 확인했고 의도한 제약(조건 2 는 해당 변수가 시작값 그대로)을 지킨 경우. 에이전트는 `submit` 이 승인된 경우만 성공으로 센다.
- 변경 거리: 변수마다 허용 범위 폭으로 나눈 차이의 유클리드 거리. 두 방식이 모두 성공한 실행끼리만 짝지어 비교한다.
- 시뮬레이터 호출: 에이전트는 `simulate` 호출 수, 기준선은 확인한 후보 수. 대리 모델 호출은 세지 않는다.
- 시간: 에이전트는 요청 해석부터 종료까지(LLM 대기 포함). 기준선은 후보 대리 모델 거름 + 시뮬레이터 확인이며 작업자 12개를 동시에 돌린 상태에서 잰 값이라 단독 실행보다 길 수 있다.

## 한계

- search 도구를 넣은 실행(맨 위 절)의 한계: 조건 2 에서 에이전트가 성공한 3건은 모두 기준선도 성공한 실행이고, 기준선이 실패한 8건은 에이전트도 실패했다. 이전 실행과 비교하면 에이전트 성공 수가 조건 1 에서 8 -> 12, 조건 2 에서 1 -> 3 이 됐다.
- 설계 A 조건 2 는 제약 해석이 `첫 타점 거리 >= 0` 으로 틀린 실행이다. search 의 첫 후보를 simulate 했을 때 1개가 남았고, 에이전트가 simulate 를 4번 쓰는 동안 모두 1개가 남아 한도로 끝났다. 같은 후보를 반복하지 말라는 지시를 프롬프트에 넣었지만 소형 모델이 늘 따르지는 않았다.
- search 는 시작 설계에 가까운 순으로 돌려주기 때문에 후보가 대리 모델의 경계 근처에 모이고, 대리 모델이 틀리는 경우 상위 후보가 함께 실패한다.
- 보강 기준선의 시뮬레이터 확인 수는 이전 확인 수와 국소 후보 확인 수의 합이라 상한이다. 보강 기준선은 국소 탐색 후보에 이전의 전역 후보 10,000개를 더한 풀을 쓰고, 에이전트의 search 는 국소 탐색 후보와 필요할 때 전역 후보 1,500개를 쓴다.
- 이번 실행의 걸린 시간은 이 평가만 돌렸을 때 값이지만, GPU 와 Ollama 는 다른 프로그램이 쓰고 있었을 수 있다.

- 표본이 작다. 시작 설계 12개, 실행당 한 번씩이고 LLM 은 같은 입력에도 응답이 달라진다. 성공률 차이(조건 1 에서 8/12 대 12/12)의 신뢰구간을 잡을 수 없는 크기이며, 변경 거리 비교는 두 방식이 모두 성공한 8건(조건 2 는 1건)만 짝지은 값이다. 시험 설계 20개를 뽑았지만 시간 때문에 앞의 10개만 돌렸다.
- 에이전트의 실패 15건은 모두 도구 호출 12회를 다 쓴 경우다. 위 trace 예시의 실패 건처럼 변수 하나씩 훑기(sensitivity)와 predict 를 반복하다가, predict 가 0개를 보인 설계를 simulate 로 확인하기 전에 한도가 끝나는 경우가 있다. 실패 원인을 건별로 분류하지는 않았다.
- 조건 2 의 기준선은 고정 변수를 시작값으로 묶고 나머지를 샘플링한 뒤 거른다. 12건 중 8건은 후보 10,000개 가운데 대리 모델을 통과한 것이 하나도 없었다. 이것이 해가 없다는 증거는 아니며, 이 샘플링으로 못 찾았다는 뜻이다. 에이전트도 그 8건에서 모두 실패했다.
- 걸린 시간은 비교 조건이 다르다. 기준선은 작업자 12개를 동시에 돌린 상태에서 쟀고, 시간 대부분이 후보 10,000개를 대리 모델에 넣는 단계(평균 1,043 s / 968 s)다. 에이전트는 한 번에 하나씩 돌렸지만 GPU 를 다른 작업과 나눠 쓰고 있어 LLM 응답 시간이 일정하지 않았다. 기준선 후보 수를 줄이면 시간이 줄어든다.
- 기준선은 `explore.py` 와 같은 방식(주변 무작위 후보 -> 대리 모델 -> 거리순 시뮬레이터 확인)을 시작 설계마다 적용한 것이다. 후보를 뽑는 분포는 시작 설계 주변 정규분포라서 최적화가 아니며, 변경 거리 0.4 안팎은 그 샘플링의 한계를 함께 반영한다.
- 소형 모델(qwen3.5:4b, think 끔)이 도구 결과를 받은 뒤 빈 응답을 내거나 설명만 하고 도구를 부르지 않는 경우가 잦았다. user 메시지로 재촉하면 빈 응답이 더 나와서, 도구 호출 없는 응답 뒤에는 같은 대화를 JSON 형식 강제(`format`)로 한 번 더 받는다. 이렇게 받은 호출이 조건 1 에서 28/94, 조건 2 에서 53/140 이다. 형식 강제 호출도 같은 도구 규칙과 한도를 거친다.
- 평가 도중 에이전트를 두 번 고쳤다. 첫 실행(도구 호출 없는 응답에 대한 처리 없음, 제약 해석 프롬프트 예시가 README 예와 같음)은 성공 조건 1 에서 8/12, 조건 2 에서 2/12 였고 `results/agent_eval_v1_before_retry_fix.json` 에 남겼다. 이 실행에서 제약 해석이 없는 요청에 `min 0` 을 만들거나, '그대로' 를 `min 60` 으로 옮기는 예가 있어 제약 해석 프롬프트의 예시를 바꿨다. 두 번째 실행(빈 응답 재샘플링 + user 재촉)은 8/12, 1/12 이고 `results/agent_eval_v2_resample_nudge.json` 에 있다. 마지막이 이 문서의 표다. 시작 설계와 요청 문장은 세 실행에서 같다. 제약 해석 프롬프트는 같은 요청 문장을 본 뒤에 고쳤으므로 해석 일치율은 낙관적이다.
- 마지막 실행에서도 제약 해석이 틀린 건이 1건 있다 (A, 조건 2: '첫 타점 거리 값은 그대로' 를 `첫 타점 거리 >= 0` 으로 해석). 이 경우 제약이 사실상 없는 상태가 되어 에이전트가 그 변수를 바꿔도 코드는 막지 못한다. 평가의 성공 판정은 의도한 제약으로 따로 확인하므로 이 실행은 실패로 센다.
- 에이전트에게 주는 첫 메시지에 시작 설계의 대리 모델 예측(못 쏘는 타점 목록)을 코드가 미리 넣는다. 이 예측은 도구 호출 수에 세지 않았다.
- 대리 모델 예측이 틀릴 수 있다. `simulate` 로 확인한 설계만 제출되므로 최종 판정에는 영향이 없지만, 거르는 단계에서 좋은 후보를 놓칠 수 있다. 시뮬레이터 자체의 가정(건 치수, 관절 한계, 판재 단순화)은 README 의 한계와 같다.
